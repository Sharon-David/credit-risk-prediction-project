\begin{abstract}
Accurate credit risk models are easy to build offline, but real-world lending also demands cost-aware decisions, real-time feature reconstruction and full audit traceability. This paper presents CreditIQ, an end-to-end credit risk prediction platform built on Amazon Web Services (AWS) and evaluated on the Home Credit Default Risk dataset. Raw data is stored in Amazon S3, explored with Amazon Athena and preprocessed by AWS Glue under AWS Step Functions orchestration. A stacked ensemble of Logistic Regression, Random Forest, XGBoost and LightGBM achieves a held-out ROC-AUC of 0.7556, and a business cost matrix that penalises false approvals far more than false rejections sets its decision threshold at 0.49. The model is hosted on an Amazon SageMaker serverless endpoint, served through Amazon CloudFront, API Gateway and AWS Lambda, and every decision is logged to Amazon DynamoDB under AWS IAM and Amazon CloudWatch governance. The cloud deployment exactly matched the predictions of the local baseline, achieved 100\% request success rate, and had a median server-side latency of just 27 ms --- a realistic example of cost-aware financial MLOps.
\end{abstract}

\begin{IEEEkeywords}
MLOps, Credit Risk Prediction, Cloud Computing, Amazon Web Services (AWS), Stacked Ensemble, Cost-Sensitive Learning, Serverless Inference.

\section{INTRODUCTION}
The lending of money to consumers is now one of the most data-dependent activities in today's finance. Each loan application includes dozens of demographic, financial and behavioural characteristics and the lender must make a decision on the application within seconds and be held responsible to regulators for the rationale behind that decision. While it is easy to make a statistical credit scoring model, it is much harder to get that model to run reliably, cheaply and transparently in production.

There are two common modelling challenges to address with credit risk data. First, defaults are sparse: Only about 8\% out of 307,511 applicants in the Home Credit Default Risk dataset default, and a naive classifier can attain high accuracy by granting all the applicants a loan. Secondly, the classification error is asymmetric. If a borrower defaults on a loan, a lender will have to spend a lot more than if he or she had rejected a reliable borrower, making the 0.5 ``probability cutoff'' the wrong point on which to run a business.

Operational challenges are also great. Unfortunately, many data science projects never make it to production due to disjointed tooling and siloed handoffs \cite{2}. The service must be live and be able to be rebuilt from the subset of the partial inputs that the loan officer actually types; it must have low latency and deal with unpredictable traffic volumes; and it must record each time it makes a prediction for later audit. Monolithic, always-on servers don't fare well with these requirements: during periods of inactivity they waste compute, and during periods of high traffic, they become a single point of failure.

A typical cloud MLOps lifecycle (Fig.~\ref{fig:mlops}) addresses these needs by moving a model from data ingestion and preparation through training, packaging and serving to continuous monitoring, which feeds back into retraining \cite{5}, \cite{6}. Each stage maps onto a managed cloud service, so the pipeline can be automated end to end rather than handed off manually between teams.

To overcome this, we present CreditIQ, an enterprise cloud-based credit risk prediction and decision platform built entirely on managed and serverless AWS services. The platform turns raw applicant data into a logged, risk-tiered lending decision in real time, within free-tier or near-free-tier cost. Our specific contributions are: (1) a six-stage modular modelling pipeline that produces a cost-optimised stacked ensemble; (2) a serverless data lake and preprocessing layer using Amazon S3, Athena and AWS Glue, orchestrated by AWS Step Functions; (3) a real-time serving path that routes requests from Amazon CloudFront through Amazon API Gateway and AWS Lambda to a containerised Amazon SageMaker serverless endpoint; and (4) an audit and observability layer built on Amazon DynamoDB, AWS IAM and Amazon CloudWatch, together with an empirical comparison of the cloud deployment against a local baseline.

\subsection{Literature Review}
This research draws on foundations of cloud-native Machine Learning Operations (MLOps), serverless inference architectures, and cost-sensitive ensemble modelling for credit risk assessment.

Pipelines to move credit scoring models from local jupyter notebooks to production are needed. M\"akinen et al. demonstrated that many data science projects fail to get to the deployment stage due to disjointed tooling and manual handoffs \cite{2}. Additionally, Continuous Integration and Continuous Delivery (CI/CD) has been shown to be integrated into cloud workflows, which helps lower technical debt and accelerate the cycle of retraining \cite{5}, \cite{8}, and managing technical debt in ML systems has been studied using end-to-end MLOps pipelines \cite{11}. Casimiro et al. have provided a separation of data ingestion from model execution to maintain cloud-native systems \cite{6} and Jiao et al. presented reference architectures for cloud-based platforms for machine learning on big data \cite{4}. To eliminate the preprocessing slowdown that typically occurs in feature engineering for large tabular datasets, Rani and Kumar discovered that they could run distributed extract-transform-load (ETL) jobs using AWS Glue and Amazon S3 at the data storage and processing layer \cite{9}.

Serving these pipelines for real-time lending decisions introduces practical challenges around latency, workflow orchestration and regulatory compliance. Symeonides et al. and Zhang et al. conducted studies to compare the costs of serverless deployments with those of traditional containers and discovered that serverless deployments can reduce the idle compute cost when the prediction traffic is irregular \cite{1}, \cite{7}. Rastegar et al. proposed serverless architectures for machine learning model deployment \cite{3}, and Bhatt et al. confirmed that pairing AWS Lambda with Amazon API Gateway handles low-latency inference reliably \cite{10}. Comparative studies of fully managed platforms such as AWS SageMaker against custom serverless pipelines highlight the trade-off between operational convenience and control \cite{13}, while P. P. et al. showed that managing multi-step training and scoring workflows with AWS Step Functions prevents silent pipeline failures \cite{14}. Because financial institutions face strict regulatory audits, K. M. and N. S. along with R. S. and M. T. stressed that cloud ML systems need strict identity access controls, continuous monitoring and immutable audit logs to track model drift and verify how individual decisions were reached \cite{12}, \cite{15}.

The prediction of loan defaults becomes difficult in the context of modelling because of the highly imbalanced class distribution and imbalanced error costs. Rofik et al. (2023) and Alamsyah et al. (2024) showed that the use of stacked ensemble of different base learners such as XGBoost, LightGBM and Random Forest can be used to get better ROC-AUC than using one of the base learners alone. However, raw probability scores are not necessarily to be interpreted as sound lending decisions. Petrides et al. (2020) and Shen et al. (2019) pointed out that standard classification cutoffs ignore the fact that approving a borrower who defaults costs a lender far more than turning away a reliable applicant, making it necessary to tune the final decision threshold against an explicit business cost matrix.

\subsection{Research Gap}
All of this collectively indicates that there is a clear gap between the credit risk modelling and cloud systems engineering. The financial losses incurred from imbalanced credit datasets can be minimized using stacked ensembles with cost sensitive thresholds, while serverless AWS services can support scalable low-latency inference pipelines separately \cite{1}, \cite{10}. However, the integration of the two has been neglected. Most of the credit scoring papers evaluate their ensembles and cost matrices in standalone local notebooks, without considering how the features are rebuilt, orchestrated and logged in a live cloud environment, and most of the papers showcasing cloud MLOps papers use standard (non-weighted) classifiers, which ignore the difference between classification errors. The contribution claimed here is therefore neither a standalone stacking method nor a generic serverless inference setup: it is the end-to-end implementation of a cost-optimised stacked ensemble inside an orchestrated AWS pipeline (combining S3, Athena, Glue, SageMaker, Step Functions, Lambda and DynamoDB) that turns raw applicant inputs into logged, risk-tiered lending decisions in real time.

\section{SYSTEM ARCHITECTURE \& METHODOLOGY}

\begin{figure}[htbp]
\centerline{\includegraphics[width=\columnwidth]{system_architecture.png}}
\caption{High-level overview of the CreditIQ cloud architecture on AWS.}
\label{fig:sysarch}
\end{figure}

The CreditIQ design splits into an offline data and training path and an online serving path that share one artifact store (Amazon S3). Datasets and artifacts are stored in S3, explored with Athena, processed with Glue and hosted on SageMaker. Real-time predictions flow from a static user interface on CloudFront through API Gateway and Lambda, while every prediction is written to DynamoDB, the pipeline is orchestrated by Step Functions, access is governed by IAM, and all components are monitored by CloudWatch. Fig.~\ref{fig:sysarch} summarises the architecture, which we organise into three parts: (1) governance and observability (IAM, Step Functions, CloudWatch); (2) the offline pipeline (S3, Athena, Glue, SageMaker); and (3) serverless hosting and real-time inference (CloudFront, API Gateway, Lambda, DynamoDB).

\subsection{Problem Formulation and Dataset}
The platform predicts whether a consumer will default on a loan (Home Credit Default Risk - application\_train.csv) comprising approximately 160 MB, 307,511 rows and 122 columns. The target is also extremely imbalanced with 282,686 non-defaulters (91.9\%) and 24,825 defaulters (8.1\%). A 40\% stratified sample of 123,004 applicants is used for modelling purposes to maintain a low compute cost, while keeping the class ratio. The system estimate the default probability $p = P(y=1 \mid \mathbf{x})$ of an applicant feature vector $\mathbf{x}$ and maps it to an operational decision.

\subsection{Layer 1: Data Lake and Exploratory Querying (S3 + Athena)}
The raw data is loaded into an S3 bucket, which serves as the central data lake, using different prefixes for raw data, processed outputs, model artifacts and query results. Amazon Athena processes the raw CSV file as if it were a local file without loading it into local memory, using the OpenCSVSerde serializer to define an external table that defines the file. Exploratory queries inspect row counts, missingness percentages, income and credit distributions, the frequency of the 365243 sentinel in DAYS\_EMPLOYED, and the severe class imbalance, reproducing the analysis of the first notebook stage without provisioning any compute.

\subsection{Layer 2: Preprocessing and Feature Engineering (Glue)}
Triggered by Step Functions, a serverless AWS Glue Python Shell job reads the raw CSV from S3, replaces the 365243 sentinel in DAYS\_EMPLOYED with a missing value, derives financial ratio features and removes every column with more than 45\% missing values before writing the cleaned dataset back to the processed/ prefix. In the modelling pipeline the same logic is extended into nine domain features: five financial ratios (CREDIT\_INCOME\_RATIO, ANNUITY\_INCOME\_RATIO, CREDIT\_DURATION\_RATIO, GOODS\_CREDIT\_RATIO, INCOME\_PER\_PERSON), three demographic and career stability metrics (AGE\_YEARS, YEARS\_EMPLOYED, EMPLOYED\_AGE\_RATIO) and DOC\_COUNT. For example,
\begin{equation}
\text{CREDIT\_INCOME\_RATIO} = \frac{\text{AMT\_CREDIT}}{\text{AMT\_INCOME\_TOTAL}}.
\end{equation}
After dropping SK\_ID\_CURR and the sparse columns, 80 input features remain (68 numeric and 12 categorical). A scikit-learn ColumnTransformer applies median imputation and standard scaling to numeric features, and constant imputation followed by one-hot encoding with handle\_unknown=``ignore'' to categorical features, producing a 192-dimensional design matrix. An 80/20 stratified split yields 98,403 training and 24,601 test records. The fitted transformer is persisted as preprocessor.pkl together with a schema contract, feature\_columns.json.

\subsection{Layer 3: Model Training, Stacking and Cost Optimisation}
Five base classifiers are trained with algorithmic class-imbalance handling: Logistic Regression (class\_weight=``balanced'', saga solver), Random Forest, scikit-learn Gradient Boosting, XGBoost (scale\_pos\_weight set to the negative-to-positive ratio) and LightGBM. Four of them (Logistic Regression, Random Forest, XGBoost and LightGBM) are then combined in a 5-fold cross-validated StackingClassifier whose Logistic Regression meta-estimator blends the out-of-fold probabilities. The ensemble is serialised as stacked\_model.pkl.

Raw probabilities are converted into decisions with a business cost matrix in which a false approval of a defaulting borrower costs 12,000 and a false rejection of a creditworthy borrower costs 2,500. The decision threshold is selected as
\begin{equation}
\tau^{*} = \arg\min_{\tau \in [0.02,\,0.50]} \; C_{\mathrm{FA}}\,N_{\mathrm{FA}}(\tau) + C_{\mathrm{FR}}\,N_{\mathrm{FR}}(\tau),
\end{equation}
where $N_{\mathrm{FA}}$ and $N_{\mathrm{FR}}$ are the counts of false approvals and false rejections at threshold $\tau$. The scan gives $\tau^{*} = 0.49$, stored as optimal\_threshold.txt. The six stages (exploration, preprocessing, base models, stacking, threshold optimisation and evaluation) are implemented as modular notebooks so that each artifact can be regenerated independently.

\subsection{Layer 4: Real-Time Serverless Serving and Audit Logging}
\subsubsection{Model Hosting (Amazon SageMaker)}
The trained artifacts are packaged as model.tar.gz, promoted to S3 and hosted on a SageMaker serverless inference endpoint with 4,096 MB of memory. Because the ensemble depends on recent versions of scikit-learn, XGBoost and LightGBM, it is served from a custom container image stored in Amazon Elastic Container Registry (ECR). The container exposes the SageMaker /ping and /invocations contract using a thin Flask application, and uses the same scoring module (predict\_single.py) in the cloud as is used locally, ensuring that the same code is run in the cloud. Serverless inference charges only for compute time used by requests and automatically scales down to zero when not in use.

\subsubsection{On-the-Fly Feature Reconstruction}
A loan officer typically knows only a handful of fields. The scoring module therefore merges the caller's partial parameters over a baseline dictionary of typical applicant values, recomputes the nine engineered features from the merged record, aligns the columns to the exact schema the preprocessor was fitted on, transforms the record and calls predict\_proba() on the stacked ensemble.

\subsubsection{Tiered Decisioning}
The default probability $p$ is anchored on the cost-optimal threshold $\tau^{*}$ and mapped to an operational tier, as shown in Table~\ref{tab:tiers}.

\subsubsection{API Routing and Auditing (API Gateway, Lambda, DynamoDB)}
The static single-page application (credit-risk-demo.html, branded ``CreditIQ'') is hosted in a private S3 bucket and distributed globally over HTTPS by CloudFront using Origin Access Control. When the user submits the form, the browser issues an HTTPS GET /predict request with query parameters to an API Gateway HTTP API, which triggers a Python Lambda function. Lambda maps the user-facing parameters to model columns, invokes the SageMaker endpoint, and, before returning the JSON response, writes the full transaction record (applicant ID, raw inputs, probability, tier, decision and UTC timestamp) to a DynamoDB table that uses the applicant ID as partition key and the timestamp as sort key.

\subsection{Layer 5: Security, Orchestration and Observability}
The pipeline is orchestrated by AWS Step Functions as a state machine, which runs the Glue job synchronously, and passes to a failure state if it fails (rather than failing silently) \cite{14}. No long-lived credentials are hardcoded in the code---the execution identity that you use for AWS IAM Glue includes a trust policy for Glue, SageMaker, Lambda and Step Functions. Amazon CloudWatch collects logs from Glue, SageMaker and Lambda, monitors the latency of API Gateway, and triggers alarms when Lambda errors occur \cite{15}.

\section{TECHNOLOGY STACK}
CreditIQ combines a compact Python modelling stack with a set of managed AWS services, each chosen because its execution and pricing model matches the workload it serves.

\subsection{Software and Libraries}
\textbf{Python, Pandas and NumPy}: Python is the only language used across the notebooks, the command-line scorer, the FastAPI service, the Glue job, the Lambda function and the SageMaker container. Pandas and NumPy load and sentinel-clean the data, filter columns by missingness and calculate the nine engineered features.

\textbf{Scikit-learn, XGBoost and LightGBM}: Scikit-learn provides the ColumnTransformer, stratified splitting, Logistic Regression, Random Forest, Gradient Boosting and the cross-validated StackingClassifier. XGBoost and LightGBM supply cost-weighted and leaf-wise gradient boosting respectively, which are well suited to high-dimensional tabular data.

\textbf{Joblib, Matplotlib and Seaborn}: Joblib serialises the preprocessor and models for inference, while Matplotlib and Seaborn produce the exploratory plots, ROC comparisons, cost curves and confusion matrices.

\textbf{FastAPI, Flask and Boto3}: FastAPI (predict\_api.py) serves the local baseline, Flask implements the SageMaker container contract, and Boto3 connects Lambda and Glue to S3, SageMaker Runtime and DynamoDB.

\textbf{HTML5, CSS3 and Vanilla JavaScript}: The CreditIQ interface is a single-page, zero-build form that sends inputs to /predict and displays the probability, tier and decision.

\subsection{AWS Services}
Each AWS service was selected because its execution and pricing model matches the workload it serves: storage and query services for the offline data path, scale-to-zero compute for the bursty serving path, and managed governance services that require no infrastructure of their own. Table~\ref{tab:cost} lists the pricing model and the measured cost of each service for the evaluation workload.

\textbf{Amazon S3 (Simple Storage Service)}: S3 is an object storage service designed for 11 nines of durability, which stores data as objects in buckets, specified by key prefixes. In CreditIQ it is the main data lake and the common artefact store shared by the offline and online routes. The raw/ prefix is for the original dataset, processed/ contains Glue outputs, athena-results/ contains the query results, and the model bundle (model.tar.gz) is stored where SageMaker can load it. A separate private bucket, only accessible via CloudFront, holds the static website. Because all other services read from and write to S3 storage, data is transferred to and from it without ever traversing a long-running server \cite{9}.

\textbf{Amazon Athena}: Athena is a serverless, interactive query engine that operates on S3 with native SQL, with schemas defined on the fly as queries are made over the data rather than by loading it into a database. CreditIQ creates an external table, a logical definition over the raw CSV, and uses it for exploratory analysis: row counts, missingness, income and credit distributions, sentinel values and class imbalance. Athena charges \$5.00 per TB scanned, so each query over the 160 MB dataset costs a fraction of a cent and the exploration stage needs no compute when not in use.

\textbf{AWS Glue}: Glue is a serverless data integration service for extract, transform and load (ETL) jobs. CreditIQ uses a Glue Python Shell job, running a plain Python script with pandas on managed capacity billed on a DPU-minute basis. The job reads the raw CSV from S3, fixes the 365243 sentinel, derives ratio features, removes sparse columns and writes the cleaned output back to S3. This step takes the place of a manual notebook run with a repeatable, schedulable job whose logs flow automatically to CloudWatch \cite{9}.

\textbf{Amazon SageMaker}: SageMaker is AWS's fully managed machine learning platform for training, hosting and monitoring models \cite{13}. CreditIQ leverages SageMaker serverless inference, in which AWS provides compute resources automatically for each request and scales to zero when the endpoint is idle, charging only for the compute time consumed. The stacked ensemble is served from a custom container image stored in Amazon Elastic Container Registry (ECR), which pins the exact scikit-learn, XGBoost and LightGBM versions the model was trained with and implements the standard /ping and /invocations contract. This removes any dependency on the library versions offered by prebuilt framework images.

\textbf{AWS Lambda}: Lambda is an event-driven, Function-as-a-Service compute platform that runs code with no servers to manage, billed per request and per millisecond of execution \cite{1}, \cite{7}. The CreditIQ Lambda function is the glue of the serving path: it maps the query parameters visible to users onto model columns, invokes the SageMaker endpoint, writes the audit record to DynamoDB and returns the JSON response with the cross-origin headers that the browser needs. Because it holds no model in memory, the function remains small and starts quickly.

\textbf{Amazon API Gateway}: API Gateway is a managed service for creating and publishing HTTPS APIs. CreditIQ uses HTTP API, the lower-cost, lower-latency API Gateway variant, with a simple GET /predict route integrated with the Lambda function \cite{10}. It offers a secure public HTTPS endpoint, request routing and automatic latency and error metrics in CloudWatch, with no web server to run.

\textbf{Amazon CloudFront}: CloudFront is AWS's content delivery network, distributed globally, which stores content at edge locations around the world and serves it over HTTPS. CreditIQ uses it to deliver the single-page CreditIQ interface from a private S3 bucket through Origin Access Control, so the bucket is never publicly exposed. The interface is delivered from the edge location closest to the user, with HTTPS provided by default.

\textbf{Amazon DynamoDB}: DynamoDB is a fully managed NoSQL key-value and document database with single-digit millisecond latency and on-demand scaling. CreditIQ uses it as the audit store: each prediction is written as one item keyed by the applicant ID (partition key) and the UTC timestamp (sort key), storing the raw inputs, probability, risk tier and decision. This schema lets an auditor get the full decision history of any applicant in a single query, which is pivotal to regulatory compliance and traceability \cite{12}.

\textbf{AWS Step Functions}: Step Functions is a serverless workflow orchestrator that allows a pipeline to be written as a state machine in the Amazon States Language. CreditIQ's state machine begins the Glue job with the startJobRun.sync integration, waits for it to finish and routes any failure to an explicit failure state. A visual record is made of each execution showing which state succeeded or failed, which prevents silent pipeline failures \cite{14}.

\textbf{AWS IAM (Identity and Access Management)}: IAM defines who or what is allowed to access each AWS resource. CreditIQ gives its services a role with a trust policy that permits Glue, SageMaker, Lambda and Step Functions to assume it. Each service is thus issued short-lived credentials at runtime rather than long-lived access keys embedded in code \cite{12}.

\textbf{Amazon CloudWatch}: CloudWatch is AWS's logs, metrics and alarms service for monitoring and observability. CreditIQ uses it to collect the Glue job output, the Lambda and SageMaker logs, and the API Gateway latency and error metrics used in Section~\ref{sec:results}, with an alarm on Lambda errors. Every component of the platform is monitored from a single location with no agent to install \cite{15}.

\section{IMPLEMENTATION METHODOLOGY}
Development followed a phase-based process. The modelling pipeline was built first as six modular notebooks, each consuming the artifacts of the previous stage, so that the preprocessor, the base models, the stacked ensemble and the threshold could be regenerated independently. The scoring logic was then extracted into a single reusable module (predict\_single.py) and validated locally through a FastAPI service, which became the latency and correctness baseline for the cloud deployment.

The cloud deployment was then divided into three independently deployable domains, each owned by a different team member and hosted in a separate AWS account: (A) the data pipeline (S3, Athena, Glue, Step Functions); (B) model serving (ECR, SageMaker, Lambda, API Gateway, DynamoDB); and (C) content delivery (S3, CloudFront). The only contract between the serving and delivery domains is the public API Gateway URL, and the data pipeline is fully independent. This separation allowed all three domains to be built in parallel and limits the blast radius of any misconfiguration to a single account. Because the SageMaker container reuses the same scoring module as the local baseline, functional parity between local and cloud inference is preserved by construction.

Local measurements were taken on a laptop running the FastAPI service on localhost; cloud measurements were taken against the deployed AWS stack in the us-east-1 region.

\subsection{Functional Validation of the Cloud Pipeline}
Every component of the architecture was exercised end to end. Athena queried the raw CSV directly from S3 and reproduced the class distribution of 282,686 to 24,825, scanning 158.4 MB per query. The Glue job completed in 1 min 52 s and the Step Functions execution, including job start-up, completed in 2 min 31 s with every state succeeding. On the serving side, 1,000 consecutive predictions were submitted through the CloudFront interface and API: all 1,000 returned HTTP 200, all 1,000 audit records were persisted to DynamoDB with an average item size of 0.9 KB, and Lambda, SageMaker and Glue logs were visible in CloudWatch. For a fixed set of 500 test applicants, the probabilities returned by the cloud endpoint were bit-identical to those of the local baseline (maximum absolute difference 0.0), confirming that containerising the scoring module introduced no numerical drift.

\section{FUTURE SCOPE}
Two extensions would move CreditIQ closer to a production lending platform. First, the serving stack can be deployed across multiple AWS regions, including one close to end users such as ap-south-1, with automatic failover between them, which would cut the network round trip and keep the platform available during a regional outage. Second, security can be hardened by replacing the shared execution role with per-service least-privilege policies, authenticating API callers with Amazon Cognito, and encrypting the audit table and buckets with customer-managed keys \cite{12}.

\section{CONCLUSION}
This paper presented CreditIQ, a cloud-based platform that integrates a cost-optimised stacked ensemble for credit risk prediction into an orchestrated, serverless AWS pipeline. Trained on the Home Credit Default Risk dataset, the four-model ensemble achieved a held-out ROC-AUC of 0.7556, and a business cost matrix fixed its decision threshold at 0.49, at which it identifies 70\% of defaulters. Deployed through S3, Athena, Glue, SageMaker, API Gateway, Lambda, CloudFront, DynamoDB, Step Functions, IAM and CloudWatch, the platform turns partial applicant inputs into logged, risk-tiered lending decisions in real time, with predictions identical to the local baseline, a 100\% success rate, only 27 ms of additional median server-side latency and a total evaluation cost under one US dollar. By closing the gap between cost-sensitive credit modelling and cloud systems engineering, CreditIQ demonstrates a practical, reproducible blueprint for auditable financial MLOps \cite{2}, \cite{6}.
